# 工作台浏览器测试与 UX 改善审计

日期：2026-08-13

审计对象：`personal-ai-workbench` v1.2.0，提交 `11263a8`

审计范围：当前本机部署、内置浏览器可见页面、自动化测试、用户提供的双栏任务清单参考图。

本次动作：只记录测试结果和问题，不修改产品代码、状态结构、真实业务数据或飞书内容。

## 1. 结论

工作台的业务护栏和技术底座已经比较完整，但界面还停留在“把能力全部展示出来”的阶段，没有收敛成“每天可以快速扫一眼、快速决定、快速离开”的个人工作台。

最主要的问题不是配色，而是信息架构：左侧导航、中间今日页、右侧 AI 同时展示大量说明、状态标签、卡片和入口，三处都在争夺注意力。当前“全部待办”也只有按完成状态和截止日期排序的单列表，没有“重要/紧急”数据，因此无法真正实现四象限。

参考图值得吸收的是：日程和待办分区、短输入区、列表层级清楚、任务状态一眼可见。不能直接照搬的是“AI 自动排优先级”：这会违反本项目已经确定的“AI 不替用户安排”规则。

建议方向是：保留左侧人工面板和右侧 AI 面板，但让中间区域成为唯一主焦点；四象限只管理正式待办；固定时间事项继续单列为日程；AI 可以提出象限建议，但所有象限落位、加入今日和截止日期变更仍由用户确认。

## 2. 证据边界

### 已验证事实

- 本机健康接口返回 `200`，版本 `1.2.0`，密码保护和 AI 配置均已启用。
- 内置浏览器中，今日、收件箱、全部待办、工作日志、待确认、待归类、逾期、归档和 4 个业务板块共 12 个路由均能打开；每页同时保留左侧导航和右侧 AI 面板。
- 收件箱飞书来源可见并完成读回；设置、新建项目、备份、AI 只读 MCP、今日手动加入/移出等核心流程此前已完成浏览器实测。
- 当前内置浏览器控制台没有 error 或 warning。
- `npm test` 新鲜运行结果为 `231/231 PASS`，失败数为 0。
- 今日计划仍为空；早晨对话接口调用没有自动改写今日计划。
- 当前 UI 中，“帮我过一下今天”可见按钮数量为 0；AI 面板“折叠/收起”按钮数量为 0；对话“收藏/星标”按钮数量为 0。

### 未证明或不能宣称的事项

- 页面显示 `gpt-5.6-luna / xhigh` 只证明配置被读取，不证明本次请求真实到达该模型；当前环境存在 Provider 不可达后使用本地安全回退的情况。
- 自动化测试使用 fake Provider / fake Feishu，不等同于真实外部系统端到端验收。
- 本报告没有重新写入或删除飞书测试数据，也没有操作 iOS 快捷指令。

## 3. 参考图中可借鉴与不可照搬的部分

### 可借鉴

1. 输入区只有“事项、属性、日期、添加”，动作链短。
2. 固定时间的日程与普通待办分成独立卡片，用户不必从一个长列表里辨认时间承诺。
3. 任务行只显示完成框、标题、一个关键标签，噪声较少。
4. 对话和结果面板并排，人的表达与结构化结果形成即时对应。

### 不可直接照搬

1. 参考图用“紧急/重要/普通”直接表达 AI 排序结果；本工作台不能让 AI 静默决定象限。
2. “普通”不是四象限中的一个象限；四象限需要两个独立布尔维度：`重要` 与 `紧急`。
3. 有具体时间的日程不是“紧急重要”的同义词。固定时间承诺应单独展示，再根据用户决定映射象限。
4. 本项目还包含项目、飞书真源、Git、待确认等上下文，不能退化成只存浏览器本地数据的轻量 Todo 页。

## 4. 已确认的问题清单

优先级说明：P0 阻断关键闭环；P1 明显影响日常使用或规则正确性；P2 影响效率与清晰度；P3 属于一致性和打磨。

### P1-01：待办没有四象限所需的数据模型

**事实**：待办当前只有标题、上下文、截止日期、项目归属、完成状态等字段。编辑弹层也只有标题、来龙去脉和截止日期。`全部待办` 仅按“未完成优先 + 截止日期”排序。

**影响**：无法区分“重要且紧急、重要不紧急、紧急不重要、不重要不紧急”，也无法稳定筛选、统计或让 MCP 读写象限。

**建议**：后续设计两个显式维度，而不是单一 `priority` 文本：

- `importance`: `important | not_important`
- `urgency`: `urgent | not_urgent`

创建待办时必须由用户选择；AI 只能生成待确认的建议。如果历史待办缺少维度，进入“未分象限”，不能静默猜测。

**验收方向**：状态校验、备份恢复、REST、MCP、收件箱转待办、编辑弹层和迁移测试全部覆盖这两个维度。

### P1-02：四象限不能与“今日计划”和“固定日程”混成一个概念

**事实**：当前只有截止日期，没有开始时间、结束时间或固定时间承诺；参考图却把“日程安排”和“待办事项”分开。

**影响**：如果直接把“紧急重要”当作今日列表，会再次让系统或 AI 替用户安排；如果把所有有日期事项都当日程，也会混淆截止日期和会议时间。

**建议**：保留三种正交视图：

- 四象限：判断处理策略，只作用于正式待办。
- 日程：有明确开始/结束时间的硬约束。
- 今日：用户今天明确承诺执行的待办集合。

四象限不会自动进入今日，日程也不能因为临近就自动生成待办。

### P1-03：AI 会为已完成待办生成“加入今日”预览，最终错误被泛化

**复现证据**：浏览器测试中，AI 为已完成待办生成 `todo_today` 加入今日的确认预览。确认后持久化校验拒绝 `todayPlan` 引用已完成待办，状态未损坏，但前端显示“服务器内部错误，请稍后重试”。

**根因边界**：

- 本地规划器匹配待办时未先排除 `done: true`。
- `setToday()` 没有在领域入口以明确的 4xx 业务错误拒绝已完成待办，而是到持久化校验阶段才失败。
- 服务器把非显式 4xx 异常统一脱敏为 500 文案，导致用户无法理解原因。

**建议**：规划、领域层和 HTTP 三层同时收口；返回“已完成待办不能加入今日”，并新增完整回归测试。

### P1-04：早晨对话有后端能力，却没有可发现的 UI 入口

**事实**：`/api/morning/chat` 存在并通过测试，前端事件代码也保留 `morning-start` 和 `morning-form`；但当前页面没有渲染对应按钮、对话框或输入表单。今日页还提示用户“帮我过一下今天”，右侧 AI 却把这句话当作未识别指令。

**影响**：用户看到承诺却找不到入口，形成“功能存在但不能用”的断裂。

**建议**：后续二选一并保持唯一入口：

1. 推荐：把早晨对话作为右侧 AI 的固定工作流/快捷操作；
2. 或者在今日页提供一张可展开的早晨对焦卡。

不应同时保留两套互相独立的聊天历史。

### P1-05：AI 对话框不能折叠，也没有收藏语义

**事实**：右侧 AI 固定宽度为 340–420px，桌面始终占据屏幕；当前没有折叠、收起、收藏或星标控件。对话消息只保存在前端内存，页面刷新后不会持久保存；只有早晨对话后端会保存 session。

**影响**：

- 阅读项目或四象限时，中间主面板持续被压窄。
- 一般 AI 对话无法形成可回看的工作资产。
- “收藏对话”若没有定义保存目的地，会产生第三套资料真源。

**建议**：

- 折叠：提供展开、窄条、完全收起三态；记住的是 UI 偏好，不是业务结论。
- 收藏：不要默认保存整段聊天。优先收藏“工具执行回执、用户确认的决策、可复用摘要”的结构化卡片。
- 项目型收藏写入对应飞书项目文档或只保存其记录指针；个人通用收藏需要用户另行确定唯一真源。

### P1-06：模型状态文案容易让人误以为已经真实联网

**事实**：右侧写“模型已接入 · gpt-5.6-luna”，设置页虽然补充“尚未联网验证”，但主界面没有区分 configured、live-verified、fallback。

**影响**：用户会把配置成功、本次真实调用成功和本地回退混为一谈。

**建议**：主界面显示三态，并在每次 AI 结果旁标注实际 planner：

- 已配置，未验证；
- 本次模型成功；
- 本次本地安全回退。

### P2-01：三栏同时常驻导致主任务区域过窄

**事实**：当前布局是 252px 左导航 + 中间内容 + 340–420px 右 AI。实测截图中，中间区域的统计卡、今日卡和人工决策卡被压缩成狭窄列，标题频繁换行。

**影响**：扫读效率低，四象限若直接放入现有中间宽度，会进一步拥挤。

**建议**：默认以中间任务区为主；AI 可折叠，左导航也可在较窄桌面进入图标/抽屉态。四象限桌面建议 2×2，低于合适宽度时切换为标签页或纵向分区。

### P2-02：今日页重复解释原则，真正可行动信息密度低

**事实**：“AI 不替你安排、由你拍板、今日不是 AI 的计划表、只有你明确加入”等同一规则在品牌文案、今日卡、人工决策区和 AI 脚注多次重复。

**影响**：空状态下仍出现大量卡片和说明，用户需要穿过解释才能找到任务、风险或输入框。

**建议**：原则说明收敛到首次引导、帮助入口和确认预览；日常首页只保留状态、下一步和异常。

### P2-03：顶栏动作优先级混乱

**事实**：每个页面顶栏同时放“同步所有项目进度、同步飞书收件箱、新建项目、设置”，而页面正文还有持续可见的收件箱输入框。

**影响**：高频动作、低频设置和可能耗时的同步被放在同一层级，视觉上每个按钮都像主操作。

**建议**：

- 主操作：快速记录/新建事项。
- 次操作：按当前页面上下文提供同步。
- 低频操作：设置、备份、全量同步进入更多菜单或设置页。

### P2-04：所有页面都显示同一收件箱输入框，页面上下文被削弱

**事实**：`shell()` 在所有路由顶部都渲染“记到收件箱”。

**影响**：在项目、日志、归档等页面，输入框与当前任务没有直接关系，却占据第一视觉位；用户也容易误以为输入会直接写入当前项目。

**建议**：保留全局快速记录，但改为更轻量的全局快捷入口；在收件箱页面才展开完整输入和数据来源状态，并明确“始终先进入收件箱”。

### P2-05：统计卡对空状态的价值低，且缺少行动导向

**事实**：首页固定显示 4 个数量卡；当数据为 0 时占据较大面积，却不能直接处理事项。

**影响**：界面显得“卡片很多、信息很少”。

**建议**：有数据时才突出统计；空状态合并成一条轻量状态。四象限建成后，可用四个象限数量和最临近事项替代纯数字卡。

### P2-06：工作日志过早占据今日页主体

**事实**：今日卡下方直接列出多条系统活动；日志内容与待办标题重复，占用大量纵向空间。

**影响**：历史操作比今天要决定的事项更醒目。

**建议**：默认只显示最近 1–2 条并提供“展开现场”；完整日志留在工作日志页。异常、失败和待确认应优先于普通更新日志。

### P2-07：AI 面板暴露过多实现细节，缺少用户工作流层级

**事实**：首屏显示 `AI CONTROL PLANE`、`MCP 工具`、`state.json`、`工具白名单`、三个能力胶囊等内部术语。

**影响**：这些信息对安全审计有价值，但不适合作为日常首屏主内容；真实问题“今天想完成什么”反而不够突出。

**建议**：默认展示工作流入口和最近对话；技术状态收进可展开的“连接与权限”区。确认预览仍保留工具名、参数和影响范围，不能为了清爽而移除安全信息。

### P2-08：AI 只读结果直接展示原始 JSON，不利于扫读

**事实**：AI 工具结果使用 `<pre>` 展示 JSON。

**影响**：对开发验收清楚，但对日常使用冗长；待办、项目、日志缺少人类可读的摘要卡。

**建议**：结果先渲染结构化摘要，原始 JSON 放入“查看技术详情”。确认预览仍需要显示会修改的实体和字段。

### P2-09：成功反馈依赖短暂 Toast，缺少可追踪回执

**事实**：多数操作只显示约 2.6 秒 Toast；AI 执行有聊天回读，但普通按钮操作不总有持久回执。

**影响**：同步、备份、飞书写入等动作完成后，用户容易错过结果，也难确认具体读回了什么。

**建议**：关键动作显示可关闭的结果条或活动回执，包含时间、对象、成功/失败和“查看详情”。

### P2-10：桌面到移动端的断点过于粗糙

**事实**：只在 900px 断点把 AI 面板改为 560px 高的下方区域，缺少折叠/抽屉和四象限降级策略。

**影响**：在小屏上，主任务后面追加一整块 AI，会造成长页面；未来 2×2 四象限也会失去可用性。

**建议**：移动端将 AI 设为底部抽屉；四象限改为顶部筛选标签 + 单列任务；日程独立一段。

### P3-01：视觉语言重复且边界层级不足

**事实**：统计、任务、项目、日志、空状态、提示都大量使用白色圆角卡 + 浅灰边框；标题尺寸差异小。

**影响**：所有内容都像同一层级，用户难以迅速区分主任务、背景信息、提示和历史。

**建议**：减少外层卡片数量，建立“页面区块 > 列表组 > 行项目”三级；只对需要独立交互或强调的内容使用卡片和阴影。

### P3-02：图标与中文/英文术语不统一

**事实**：左侧使用字符图标，右侧使用英文 `AI CONTROL PLANE`、`MODEL` 和英文 route 名，主体使用中文。

**影响**：界面像开发控制台和个人工作台拼接在一起。

**建议**：主界面统一中文工作语言；英文工具名仅在技术详情和审计预览出现；图标使用统一、可访问的图标集并保留文本标签。

## 5. 推荐的信息架构方向（待用户确认，不是已实施）

### 中间主面板

1. 一行轻量快速记录。
2. 今日固定日程：只显示明确时间承诺。
3. 今日已承诺任务：仍由用户明确加入。
4. 四象限待办：默认 2×2，支持只看一个象限。
5. 风险/待确认：只显示非零项。
6. 最近工作现场：折叠区。

### 右侧 AI

1. 默认可折叠，保留一个窄条入口和未读/待确认数量。
2. 顶部提供固定工作流：“早晨对焦、查看收件箱、复盘项目、整理当前页面”。
3. 普通回答、工具确认预览、工具结果三种消息视觉上分层。
4. 收藏对象是结构化结果卡，不默认收藏整段对话。
5. 收藏必须明确归属：项目飞书文档、个人通用知识入口或仅本地 UI 书签；不能形成无归属的第三真源。

### 四象限规则

| 象限 | 用户含义 | 默认系统行为 |
|---|---|---|
| Q1 重要且紧急 | 需要尽快处理 | 显示风险，不自动加入今日 |
| Q2 重要不紧急 | 需要持续推进 | 适合主动选择到今日，不自动安排 |
| Q3 紧急不重要 | 需要响应或委派 | 提醒确认处理方式，不自动委派 |
| Q4 不重要不紧急 | 可延后、删除或归档 | 保留可见，不自动删除 |

历史待办和 AI 无法可靠判断的事项进入“未分象限”。用户确认象限后才写入正式状态。

## 6. 建议实施顺序

1. 修复正确性断点：已完成待办加入今日、明确 4xx、早晨对话唯一入口。
2. 确定四象限字段、历史迁移和人工确认规则。
3. 重做待办页为四象限，并分离固定日程与今日承诺。
4. 增加 AI 面板折叠三态和工作流入口。
5. 定义收藏对象及唯一真源，再实现收藏。
6. 最后统一视觉层级、响应式和术语。

不建议先只换颜色、圆角或阴影；这样会让界面更精致，但不会解决当前的信息拥挤和任务决策问题。

## 7. 验收清单建议

- 四象限：每个待办恰好属于一个象限或“未分象限”；AI 不能静默改象限。
- 日期：待办仍必须有合法截止日期；固定日程另有明确时间字段。
- 今日：任何象限和任何日程都不能自动写入 `todayPlan`。
- 完成状态：已完成待办无法加入今日，并返回明确 4xx 文案。
- AI 折叠：展开、窄条、收起在桌面和移动端可恢复，且不丢当前确认预览。
- 收藏：收藏对象、归属、来源和读回路径明确；刷新后可恢复；不复制项目叙事真源。
- 早晨对话：UI 有唯一入口，能连续对话，但不改截止日期、象限或今日计划。

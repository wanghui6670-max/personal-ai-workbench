# Personal AI Workbench v3 — 信息来源与 AI 处理合同

> 状态：**Normative / 当前有效**  
> 生效日期：2026-08-16  
> 本文档是 Personal AI Workbench v3 的个人事项来源、飞书同步、日记解析、AI 权限与 Today 所有权的最高优先级产品合同。与本文冲突的旧 GetNote Task Sync、旧“飞书收件箱章节”或旧“整段单标签分类”描述均只视为历史兼容说明。

## 1. 一句话合同

```text
个人工作事实：飞书工作日记
→ 用户主动同步
→ first-seen / append-only 来源去重
→ 单条日记 block 提取 0–5 个原子待办
→ 只有原子待办候选进入 Workbench 待处理流
→ 用户补齐必要字段并确认
→ Workbench Todo
→ Today 仍由用户单独决定

内容素材：得到大脑 GetNote → 用户确认同步 → 自媒体内容库
状态真相：Workbench state
```

Workbench 本地 `state.json` 是任务状态、用户决定、Today 选择、项目归属等个人状态的真相源。飞书工作日记是个人工作事实的主要外部来源，但飞书中的分析、复盘、日常记录不会被复制成 Workbench 任务。

**不得再把得到大脑 `meeting_todos` 作为个人待办的产品级主来源。**

## 2. 飞书工作日记与同步合同

### 2.1 飞书允许混合记录

用户不需要为了 Workbench 重写自己的日记格式。同一份飞书工作日记可以混合包含：

- 明确待办；
- 一段文字中的多个下一步动作；
- 项目进展；
- 分析、观点、结论、策略；
- 复盘、感受、日常流水；
- 显式 `[INBOX]` 条目；
- checkbox / 列表项 / 普通段落。

兼容规则：

1. 旧文档如果存在一级标题 `收件箱`，仍可兼容读取其中 `[INBOX]` 条目。
2. 没有 `收件箱` 章节时进入 **mixed diary** 模式，读取有稳定 block ID 的 `p / checkbox / li` 内容，并保留最近 h1/h2/h3 标题路径作为上下文。
3. `[INBOX]` 与 checkbox 是“更可能包含动作”的强信号，但**不代表整段必须变成待办**。
4. 原始飞书 block 是证据单元，不等于任务单元。
5. 一个原始 block 可以提取 0 个、1 个或多个待办候选；单块最多 5 个。

### 2.2 同步必须由用户主动触发

同步接口仍为 `/api/inbox/sync`；兼容 MCP 工具名可继续保留 `feishu_inbox_sync`。

**打开、刷新工作台时不得自动拉取飞书，也不得自动恢复上一轮未完成的日记提取。**

只有以下两种用户显式动作可以启动本轮来源读取 / 提取：

- 点击 **“同步飞书”**：正常增量同步；
- 点击 **“初始化导入并提取待办 / 重新初始化”**：显式重建基线并启动一次提取。

### 2.3 日常同步是 append-only / first-seen

飞书个人日记同步采用严格的 **append-only / first-seen** 规则：

- `blockId` 是来源身份；
- `blockId` 一旦进入 `inboxAcks`，即永久视为“已经见过”；
- 普通“同步飞书”只允许从未见过的 `blockId` 进入新增处理；
- 已见过 block 后续被编辑，不重新导入、不覆盖 Workbench 本地候选、不再次触发 AI；
- 已见过 block 后续从飞书删除，不删除 Workbench 本地状态，也不删除 ACK；
- 同一个旧 `blockId` 再出现仍然跳过；
- 用户在 Workbench 删除本地候选后，来源 ACK 继续保留，因此普通同步不会让它“死灰复燃”。

同步发现新 block 后，**先做保守精确去重，再进入 AI 提取**。去重至少覆盖：

- 同一批新飞书 block；
- 当前 Workbench 待处理项；
- 已建立 Todo；
- 兼容保留的 Notes。

精确去重可以做 Unicode NFKC、空白折叠与 trim；**不得用模糊语义相似度自动删除两个不同事项。**

### 2.4 初始化 / 重新初始化

初始化是显式、可重复但高影响的来源基线重建动作：

- 首次显示“初始化导入并提取待办”；
- 完成后入口继续保留为“重新初始化”；
- 初始化可以完整扫描当前飞书工作日记并重建当前来源基线；
- 初始化完成后，普通同步重新回到 append-only / first-seen，只处理之后的新 block；
- 初始化不得删除、移动或改写飞书原文；
- 初始化后的 AI 工作仍然是“待办提取”，不是把整篇日记复制进任务系统。

## 3. AI 的职责：从一段日记提取 0–5 个原子待办

### 3.1 禁止整段单标签分类作为最终任务模型

旧规则“待办 / 项目进展 / 分析思考 / 日常记录 / 需要决定五选一”不再是当前个人飞书入口的最终处理模型。

原因：一段真实日记经常同时包含背景、复盘、观点和多个动作。把整段强制贴成一个标签，会造成两种错误：

- 把整段背景和分析误当成任务；
- 因为整段更像“分析”，而漏掉里面真正需要做的动作。

当前规范是 **Atomic Todo Extraction**：

```text
原始飞书 block
→ AI 阅读当前 block
→ 提取 0–5 个独立、具体、可执行的下一步动作
→ 原始 block 从本地待处理入口退出
→ 只留下精简后的待办候选
```

### 3.2 什么可以成为待办候选

候选必须是忠实于原文、能够独立理解并执行的下一步动作，例如：

- 补完某个明确内容；
- 跟进某个客户 / 事项；
- 联系、确认、准备、提交、发送；
- 拍摄、修改、整理、采购、发布；
- 原文明确提出的下一步处理动作。

一段里存在两个独立动作时，可以提取两个候选，而不是把整段作为一个巨大任务。

### 3.3 什么不得变成待办

下列内容本身不得自动变成待办：

- 已经发生的事实；
- 项目进展描述；
- 分析、判断、观点、原则、方法；
- 复盘和感受；
- 日常流水；
- 泛泛的“以后注意”“要重视”“记住这一点”，但没有具体动作；
- 被明确否定的动作，例如“不要发布”“不是再整理”“无需跟进”“不用修改”。

这些内容继续只保留在飞书事实源中。Workbench 不再为了“归类完整”而复制成 Notes 或项目记录。

### 3.4 日期和项目不得猜

每个提取候选可以包含：

- `text`：原子动作；
- `dueDate`：只有原文明示并能可靠转换为日期时才允许填写，否则为 null；
- `targetProjectId`：只有能唯一明确匹配当前未归档项目时才允许填写，否则为 null；
- `confidence` / `reason`：仅用于可审计说明。

AI 不得猜截止日期，不得因为“像某个项目”就强行归项目，不得自动新建项目。

## 4. 解析暂存与最终执行是两个层次

### 4.1 原始来源项

从飞书进入本地、尚未解析的项使用 `source = feishu_doc` 且 mixed diary 标记有效。它只是**临时解析队列中的证据项**，不是 Todo。

### 4.2 提取后的待办候选

原子待办使用独立暂存来源 `feishu_todo_candidate`：

- 只保存提取后的简洁动作；
- 保留对应 `feishuSourceBlockId` 作为来源指针；
- 可以保留建议日期、建议项目、提取置信度和理由；
- 不再进入原始日记 AI 提取队列；
- 仍然不是正式 Todo。

原始 block 被替换为候选以后，对应 `inboxAcks` 必须继续保留，因此普通飞书同步不会再次导入原始段落。

### 4.3 0 个待办的处理

如果一个原始 block 没有可执行待办：

- 从 Workbench 本地待处理流撤下；
- 不创建 Todo；
- 不创建 Note；
- 不写项目记录；
- 不改变 Today；
- 飞书原文与来源 ACK 保持不变。

活动日志只能记录“解析完成 / 提取数量”等安全元数据，**不得复制私人日记正文**。

### 4.4 正式 Todo 必须经过用户确认

有明确截止日期的候选可以展示“确认创建待办”；没有可靠截止日期的候选只允许要求用户补日期。

创建正式 Todo、改变项目归属等最终状态变更必须继续走领域校验与用户确认。识别成待办不代表自动创建 Todo。

`todayPlan` 与 Todo 也是两个不同领域对象：即使 Todo 已创建，也**不得自动加入 Today**。

## 5. AI 隐私与单条作用域

单条飞书日记提取必须使用最小上下文。Provider 最多看到：

- 当前目标 block 的正文；
- 当前 block 的标题路径 / 块类型；
- 最多 30 个未归档项目的目录级摘要。

不得一起发送：

- 其他 Inbox / 日记原文；
- Todo 列表正文；
- Today；
- confirmations；
- 项目长介绍或项目文档正文；
- 其他无关私人记录。

当前单条审阅能力白名单只允许针对目标 item 的：

- `diary_extract_todos`：把当前原始日记 block 转成 0–5 个本地待办候选；这是解析暂存动作，可在用户主动同步 / 初始化启动的本轮中自动执行；
- `inbox_process`：最终待办处理能力，仍受领域校验与确认边界保护。

任何跨 item、跨工具或目标不一致的计划必须 fail closed。

## 6. 今日工作面与批量处理

v3 入口仍可沿用“今日与收件箱”兼容名称，但待处理区的真实语义是：

- 原始日记：正在做待办提取；
- 待办候选：等待补日期 / 用户确认；
- 少量无法安全处理的项：需要用户决定。

默认不再长期展示“项目进展 / 分析思考 / 日常记录”工作池，因为这些内容本来就属于飞书事实源，不需要在 Workbench 再存一份。

待处理区支持：

- 多选 / 全选当前；
- 批量重新提取原始日记；
- 批量确认已经具备安全执行条件的候选；
- 批量删除 Workbench 本地项。

批量确认不得为了效率放宽校验：缺截止日期、仍在提取、项目不可靠的候选必须跳过。

批量删除使用一次确认、一次后端批处理事务（单次最多 500 条），只删除 Workbench 本地待处理项，不删除飞书原文，并保留飞书来源 ACK。

## 7. 其他来源与项目记录边界

### 7.1 GetNote

得到大脑只保留为自媒体内容来源：

- `getnote_content_status`：只读查看内容同步状态；
- `getnote_content_sync`：用户确认后同步可验证真实原文到本地内容库。

`external_tasks_sync` / `external_task_integration_update` 等旧待办工具不得重新注册为当前个人任务主入口。

固定内容目录仍为：

```text
<WORKSPACE_ROOT>/<业务序号>_自媒体/得到大脑内容/
```

### 7.2 项目记录

飞书个人工作日记中的项目进展不会因为日记解析而自动复制成项目记录。项目分析正文和总结仍通过明确的项目记录链路写入绑定的飞书项目文档；机器进度与状态继续由 Workbench state 管理。

## 8. 不可回退的硬约束

1. 打开网页不自动同步飞书、不自动恢复日记提取。
2. 普通同步只处理从未见过的新 `blockId`。
3. 不把整个飞书段落直接当作 Todo。
4. 一段允许提取 0–5 个原子待办。
5. 非待办背景不复制到 Workbench Notes / 项目记录。
6. 不猜截止日期、不猜项目、不自动新建项目。
7. 不自动加入 Today。
8. 不删除或改写飞书日记原文。
9. Provider 只接收当前 item + 有界项目目录摘要。
10. 飞书 ACK 长期保留，避免历史反复导入。
11. 批量删除只影响 Workbench 本地暂存。
12. 解析层变更不得绕过最终 Todo / Today / 项目状态的用户确认边界。

## 9. 当前推荐链路

```text
用户打开 Workbench
→ 只读本地状态

用户点击“同步飞书”
→ 拉取飞书当前文档
→ 只找 first-seen 新 blockId
→ 精确去重
→ 原始 mixed-diary block 暂存
→ 最多 2 条并发做单条 AI 原子待办提取
→ 0 个动作：原始项退出待处理
→ 1–5 个动作：替换为精简的 feishu_todo_candidate
→ 用户补充必要日期 / 项目
→ 用户确认创建 Todo
→ 是否加入 Today 再由用户单独决定
```

这条链路是当前 v3 的规范性个人事项主链。
